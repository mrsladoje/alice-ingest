# `alerting_monitors`

Provisions the OpenSearch Alerting layer on the control host: two notification
channels, one cluster setting, and 28 monitor definitions. It renders
`alerting.sh` into the shared bootstrap directory, stages the monitor JSON
beside it, and runs the script once. The script upserts every monitor by name,
so a second run updates instead of duplicating.

It is a separate role because Alerting is a different mechanism from anomaly
detection. Alerting runs saved queries on a fixed period and fires trigger
actions. The anomaly-detection plugin trains Random Cut Forest models and writes
results. The two share only the OpenSearch URL. Splitting them lets the 28
monitors and their numeric guards move without touching the detector
definitions.

## What it does

```
                              CONTROL HOST

┌─ 1. RENDER ────────────────────────────────────────────────────────────────┐
│  alerting.sh.j2  -->  /opt/alice-ingest/init/alerting.sh   0750 root:root  │
└────────────────────────────────────┬───────────────────────────────────────┘
                                     v
┌─ 2. STAGE ─────────────────────────────────────────────────────────────────┐
│  files/monitors/*.json  -->  /opt/alice-ingest/init/monitors/  0640 root   │
│  28 definitions, generated by files/gen_monitors.py                        │
└────────────────────────────────────┬───────────────────────────────────────┘
                                     v
┌─ 3. RUN alerting.sh — every deploy, against localhost:9200 ────────────────┐
│  pin_actionable_limit      persistent cluster setting                      │
│                            plugins.alerting.max_actionable_alert_count     │
│  ensure_alert_sink_alias   GATE — the alice-alert-actions write alias      │
│                            must already exist. FATAL if it does not.       │
│  upsert_channel x2         alice-incluster-alert-sink, alice-breakglass-sink│
│  upsert_monitor x28        search by name, then PUT or POST                │
│                            numeric guards re-substituted from environment  │
└────────────────────────────────────────────────────────────────────────────┘
```

The 28 monitors read four indices:

| Source index | Monitors | Period | Filled by |
|---|---|---|---|
| `cockpit-metrics` | 14 | 1 min | `cockpit_metrics` |
| `trend-rollup` | 12 | 10 min | `trend_rollup` |
| `.opendistro-anomaly-results*` | 1 (`ad-high-grade`) | 1 min | `anomaly_detection` |
| `opensearch-forecast-results*` | 1 (`disk-fill-forecast`) | 10 min | `anomaly_detection` |

## Non-obvious settings

- **`alerting.sh.j2` holds no Jinja expression.** It is still rendered with the
  `template` module. Every tunable reaches the script as an environment
  variable set by the upsert task, and each one has a shell-level fallback
  default. Keeping it a template makes the substitution point obvious and lets
  a future value be inlined without moving the file.
- **The role does not create `/opt/alice-ingest/init`.** It only writes into it.
  The directory is a shared artefact with no single owner. `alice_runtime` and
  `opensearch_bootstrap` each create it, with the same owner, group and mode.
- **`ensure_alert_sink_alias` refuses to create the sink index.** It checks that
  `alice-alert-actions` is a rollover write alias and stops the run if it is
  not. An earlier version created the name as a concrete index. That took the
  alias name and disabled retention permanently, so the sink grew without
  limit. The check is a guard against that regression, not a health probe.
- **`alice-incluster-alert-sink` notifies nobody.** It is a webhook that writes
  one document per fire into the `alice-alert-actions` write alias. It exists
  to give the 30-minute per-alert throttle a real destination. Nothing reads
  the index. Human-facing delivery goes through Alertmanager.
- **`alice-breakglass-sink` is for two monitors only.** `signal-projector-stale`
  and `alertmanager-down` post straight to the notification ingest, because
  they report the projector and Alertmanager dead. Nothing else may use it.
- **The numeric guards are baked into the JSON and then rewritten.**
  `gen_monitors.py` writes literals such as `double lagFloor = 250.0;` into the
  Painless trigger scripts. `prepare_body()` in `alerting.sh` rewrites those
  literals from the environment on every deploy. The JSON literal is only the
  fallback for a hand-run of the script.
- **`changed_when: true` on the upsert task.** The script is idempotent, but it
  cannot report whether any monitor really changed. The task reports changed on
  every run on purpose.
- **The script exits 1 on an empty `MONITORS_DIR`.** A staging failure must fail
  the deploy, not quietly provision zero monitors.

## Role variables

Values the role owns. Override any of them in `group_vars` to change them
site-wide.

| Variable | Default | Meaning |
|---|---|---|
| `dashboards_bootstrap_alerting_script` | `/opt/alice-ingest/init/alerting.sh` | Where the script is rendered and from where it is run. A literal — see couplings. |
| `dashboards_bootstrap_monitors_dir` | `/opt/alice-ingest/init/monitors` | Where the 28 definitions are staged. Passed to the script as `MONITORS_DIR`. A literal — see couplings. |
| `ad_anomaly_grade_threshold` | `0.7` | `ad-high-grade` fires above this anomaly grade. |
| `ad_anomaly_confidence_threshold` | `0.7` | `ad-high-grade` fires above this model confidence. |
| `trend_lag_floor_ms` | `250` | Lag below this is noise. The `trend-*` lag monitors ignore it. |
| `trend_entry_lag_ceiling_ms` | `3600000` | One hour. Entry lag above this is archive age, not pipeline health. |
| `trend_entity_cap_warn` | `1800` | `trend-entity-cap` warns above this many rollup entities. It sits below `trend_rollup_max_entities`. |
| `trend_min_slice_docs` | `50` | A rollup slice with fewer documents is too small to judge. |
| `trend_min_slice_errors` | `10` | Same floor, for the error-fraction monitor. |
| `trend_min_lag_docs` | `100` | Same floor, for the lag monitors. |
| `fleet_silence_fraction` | `0.5` | `fleet-fb-silence` fires when this fraction of the roster stops reporting. |
| `forecast_disk_threshold_percent` | `85` | `disk-fill-forecast` fires when the forecast crosses this filesystem fill. |

### Variables the role requires but does not own

These are site-wide. They are deliberately **not** duplicated into this role's
defaults, because a second copy is a second place to change one value.

| Variable | Owner | Used for |
|---|---|---|
| `opensearch_http_port` | `group_vars/all.yml` | `OS_URL`, the local REST endpoint the script drives. |
| `alerting_max_actionable_alert_count` | `group_vars/all.yml` | The persistent cluster setting the script pins. Also read by `anomaly_detection` and `signal_projector`. |
| `notification_ingest_port` | `group_vars/all.yml` | Builds `BREAKGLASS_SINK_URL` on loopback. Also read by `signal_projector` and `alertmanager`. |
| `dashboards_bootstrap_root` | `group_vars/all.yml` | Not read by this role. The two path defaults above must stay equal to `{{ dashboards_bootstrap_root }}/alerting.sh` and `.../monitors`. |
| `expected_monitors` | `group_vars/all.yml` | Not read by this role. `verify_detection.py`, run by `anomaly_detection` and `signal_projector`, asserts this count against the cluster. |

The two path defaults are literals, not `{{ dashboards_bootstrap_root }}/...`.
A default that reads a variable another role owns resolves lazily and makes
this role unrunnable on its own. The `alice_ops` role already does the same
for `dashboards_ops_templates_script`.

## Prerequisites

The role bootstraps nothing. Four things must be true first, all satisfied by
the role order in `playbooks/site.yml`.

| Prerequisite | Provided by | What breaks without it |
|---|---|---|
| OpenSearch answers on `localhost:9200` from the control host | `opensearch` role and the rolling-safety gate | Every curl in the script returns 000 and the first one fails the run. |
| `/opt/alice-ingest/init` exists, 0755 root:root | `alice_runtime`, and `opensearch_bootstrap` before it | The render task fails: no such directory. |
| `alice-alert-actions` is a rollover write alias | `opensearch_bootstrap`, through `templates.sh` and `ism.sh` | `ensure_alert_sink_alias` prints FATAL and the script exits 1. This is the hard one, and it is invisible from this role's own files. |
| The notification ingest listens on `127.0.0.1:{{ notification_ingest_port }}` | `signal_projector` | The two dead-man monitors upsert normally, but their break-glass webhook posts into nothing. Nothing fails at deploy time. |

The source indices are a soft prerequisite. A monitor whose index is empty or
absent upserts normally and simply does not fire. Running `cockpit_metrics`,
`trend_rollup` and `anomaly_detection` before this role gives the monitors data
to read; running them after only delays the first evaluation.

## How to use it

In a playbook, against the control host:

```yaml
- name: Alerting monitors
  hosts: control
  become: true
  roles:
    - alerting_monitors
```

- **Run it after `opensearch_bootstrap`.** The alias gate is the reason.
  `make deploy` does both in order.
- **The role is safe to re-run.** Monitors are matched by name, channels by
  configuration id, and both are updated in place.
- **To change a monitor's shape, edit `files/gen_monitors.py` and re-run it.**
  Do not hand-edit the JSON. The generator owns all 28 files, so the entity
  payload, trigger shape and identity fields cannot drift apart. It also
  deletes any stale file in `files/monitors/`.

```
python3 deploy/roles/alerting_monitors/files/gen_monitors.py
```

## Couplings

- **The two path defaults and `dashboards_bootstrap_root` change together.**
  They are written as literals here. Moving the bootstrap directory means
  editing this role's defaults as well.
- **A new monitor JSON and `expected_monitors` change together.** The count
  lives in `group_vars/all.yml` and is asserted by `verify_detection.py`, which
  the `anomaly_detection` and `signal_projector` roles run. Adding a monitor
  here fails a gate in another role until the number follows.
- **`BUCKET_MINUTES` in `gen_monitors.py` and `trend_rollup_bucket_seconds`
  change together.** The generator bakes 10 minutes into every `trend-*`
  monitor's dwell and window arithmetic. `trend_rollup` owns the 600-second
  bucket. A mismatch makes the trend monitors read partial buckets.
- **`gen_monitors.py` reads `signal_catalog.json` from the `alice_runtime`
  role.** Entity kinds and notification scopes come from that file. The path is
  relative, `../../alice_runtime/files/signal_catalog.json`. Moving either role
  directory breaks the generator, which is a build-time break, not a deploy
  break.
- **`trend_entity_cap_warn` must stay below `trend_rollup_max_entities`.** The
  warning exists to give warning before the rollup starts dropping entities.
  `trend_rollup` owns the cap.
- **The channel ids are literals in three places.** `alerting.sh.j2` creates
  `alice-incluster-alert-sink` and `alice-breakglass-sink`, every monitor JSON
  names one of them in its trigger action, and `verify_detection.py` asserts
  the channel and the 30-minute throttle on every expected monitor. A variable
  here would only let one end of the set move.

## Upstream roles rejected

No candidate was adopted, and none was found worth a row. The substance of this
role is 28 site-specific monitor definitions and their trigger scripts. No
published role ships them. What remains is a curl upsert loop of about twenty
lines against a plugin REST API, which is smaller than the configuration a
generic role would need.

The Galaxy and GitHub search behind the `opensearch` role, run in August 2026,
found no role that provisions OpenSearch Alerting monitors at all. That search
was not repeated for this role.

**Re-open this decision** if the OpenSearch project publishes a monitor
provisioning module for Ansible.
