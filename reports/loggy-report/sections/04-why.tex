\section{Why these choices}\label{sec:why}

Each subsection below takes one choice in the design. It states the job the choice must do, the options we weighed, the fact that decided it, and the cost we accepted. Section~\ref{sec:eval} gives the measurements behind the numbers.

\subsection{The collector: Fluent Bit}\label{sec:why-collector}

A collector is a small program that runs on every worker, beside the programs that write the logs. It reads each new line from a file, a socket or the journal. It parses the fields out of the text, decides where the line belongs and sends it on. It stores nothing itself. It shares a machine whose real job is reconstruction, so it must be small, and it must not need a second language runtime installed beside it.

Maturity and size decided it. Table~\ref{tab:collectors} lists the four candidates. \textit{Fluent Bit}~\cite{ref:fluentbit} is written in C and needs no other packages unless a plugin asks for one. Its vendor gives about 450~KB of memory for an idle pipeline, against more than 60~MB for \textit{Fluentd}~\cite{ref:fluentcompare}. Under our load it peaked between 133 and 228~MB, because the memory holds the chunks of records in flight, not the program (Section~\ref{sec:design-collector}). \textit{Fluent Bit} belongs to the \textit{Fluentd} project, which graduated at the Cloud Native Computing Foundation (CNCF) in 2019~\cite{ref:cncffluentd}. Graduated is the foundation's highest maturity level. It means a neutral foundation holds the roadmap, so no single company controls it.

\textit{Fluentd} is the same project one size up, and the older of the two. Its core is \textit{Ruby}, and it installs as a \textit{Ruby} package that pulls in other packages. We did not want a \textit{Ruby} package tree on every worker. \textit{Vector} is small and fast, and published benchmarks disagree on which of \textit{Vector} and \textit{Fluent Bit} is smaller. Datadog bought the company that builds \textit{Vector} in 2021, so one company decides its future~\cite{ref:vector}. \textit{Telegraf} is a good agent for a different job. ALICE already runs it to gather machine and service metrics. It emits line protocol: a name, tags, numbers and a timestamp. That format carries metrics and has no place for the free text of a log line.

\paragraph{Why not a message queue at the edge}
A message queue such as \textit{Kafka}~\cite{ref:kafka} moves records between programs. It does not make them. It cannot tail a file, parse a line or stamp a clock, so a forwarder still runs in front of it. The queue itself costs at least three more machines, its brokers, which must keep a quorum among themselves. Section~\ref{sec:why-kafka-store} covers a queue behind the collector instead.

\subsection{The store: OpenSearch}\label{sec:why-store}

The store must do three things. It must index every field and the full message body, so a person can search for any word. It must count over time, for example errors per host per minute. It must also detect anomalies and raise alerts itself, so that we do not build and run that machinery beside it. An open licence was the floor, and detection decided it.

\textit{OpenSearch}~\cite{ref:opensearch} is a search engine and document store. It began in 2021 as the open-source fork of \textit{Elasticsearch}. It is licensed Apache 2.0, and since September 2024 the \textit{OpenSearch} Software Foundation, part of the Linux Foundation, governs it~\cite{ref:osf}. Its standard package ships plugins for anomaly detection, alerting and notifications, so the detectors and monitors of Section~\ref{sec:design-watch} run inside the cluster that holds the logs. CERN IT's own monitoring service runs \textit{OpenSearch}, so CERN already operates it.

\textit{Elasticsearch} answers the same questions. One company holds it, and its source is offered under three licences: the Server Side Public License, the Elastic License and, since 2024, the AGPL~\cite{ref:elasticlicence}. Its machine-learning anomaly detection is in the paid Platinum and Enterprise tiers only~\cite{ref:elasticsubs}. With \textit{Elasticsearch} the detection half of this project becomes a purchase.

\textit{ClickHouse} is a column store under Apache 2.0, run by one company. It compresses logs well and counts fast, so it wins on disk. It ships no anomaly detection and no alerting, so it loses on machinery. We would write, run and keep alive the 17 detectors and 30 monitors of Section~\ref{sec:design-watch} ourselves.

\textit{Loki}, from \textit{Grafana} Labs, is under the AGPL. It indexes a small set of labels per stream, such as the host and the application, and not the text of the line~\cite{ref:lokilabels}. A search for a word, or a count of error lines per host, reads and filters every stored chunk in the time range. It ships no anomaly detection.

We accept two costs. Every index and every shard takes memory on the \textit{Java} heap, so the number of indices is capped. Every plugin must match the exact release of \textit{OpenSearch} it runs in, so an upgrade moves the whole set at once.

\subsection{One \textit{OpenSearch} cluster, not many clusters joined by cross-cluster search}\label{sec:why-cluster}

Every worker keeps its own info lines on its own disk. A person still needs to search all of those disks at once. We make every machine part of one \textit{OpenSearch} cluster, and ask it once.

\paragraph{Terms}
An \textit{OpenSearch} cluster is a set of \textit{OpenSearch} processes, called nodes, that share one view of which indices exist and where their pieces live. That shared view is the cluster state. The cluster manager is the one node that keeps the cluster state and sends every change to the other nodes. In \loggy{} only the three storage nodes can become cluster manager, and two of the three must agree to elect one. A worker's node holds data and answers searches. It never manages the cluster.

\paragraph{The first way: one cluster}
All machines join one \textit{OpenSearch} cluster. \textit{OpenSearch Dashboards} sends a query to one node, which acts as the coordinating node for that query. In \loggy{} that is a storage node. It reads from the cluster state which nodes hold shards of the indices asked for. It sends the query to each of them, waits for their partial answers, merges them and returns one result. The person writes one query over one index pattern, for example every application-log index, and never needs to know which machine holds what.

\paragraph{The second way: many clusters}
Each worker runs its own small cluster, and a central cluster joins them with cross-cluster search~\cite{ref:ccs}. Cross-cluster search lets a query on one cluster name indices on other clusters, written as \code{cluster:index}. Every remote cluster is registered by name on the central one, which keeps three open connections to each by default and forwards the query to all of them~\cite{ref:ccsforum}. Table~\ref{tab:clusters} sets the two ways side by side.

\paragraph{Why one cluster}
First, a worker must not manage a cluster. With many clusters, each worker is a one-node cluster and so its own cluster manager, with its own cluster state, index templates, lifecycle policies and users. That breaks the objective that workers stay cheap (Section~\ref{sec:problem-objectives}). Second, one cluster places shards and replicas itself across all machines, and the tier rule lives in index templates in one place. Third, one cluster has one set of users, roles and saved searches. Across clusters, a detector that reads a remote index needs a role that exists on both clusters and maps to the same user~\cite{ref:adsecurity}. At 200 workers that is 200 copies to keep identical. Fourth, detection and alerting read every index with no remote step. Fifth, there is no federation layer of our own to write and keep alive. Nothing has to register a new worker as a remote cluster, or remove it when it leaves.

Scale does not rule cross-cluster search out, but it does not favour it. \textit{OpenSearch} sets no hard limit on remote clusters. Each one adds connections and a round trip, and the project states that more remote clusters mean fewer queries a second and higher latency~\cite{ref:ccsforum}. We found no published deployment of cross-cluster search over hundreds of remote clusters. A single cluster of that size is documented: Amazon's managed \textit{OpenSearch} has run single clusters of up to 1,000 data nodes since late 2024~\cite{ref:aws1000}. Those clusters use dedicated cluster managers, and ours do not.

\paragraph{What we accept: fanout}
Every machine pays. A search over all worker indices reaches every worker, so every worker spends processor time on it. The answer is as slow as the slowest machine. Those machines reconstruct events, which is their real job, and log search must not compete with it. So we ask the cluster only when we must. The live lane covers watching what arrives now, and it never asks the cluster. A question such as ``which machines saw this error in run 561234?'' still has to ask all of them. Two more costs follow from one cluster: every machine upgrades in the same window, and one bad query can slow every machine. Three hundred data nodes in one cluster, one per worker in the archive, with managers that also hold data, is not tested (Section~\ref{sec:limits-design}).

\subsection{Two tiers, split by severity}\label{sec:why-severity}

An index is split into shards, and a replica is a copy of a shard on another node. A tier is a group of nodes that holds one kind of index. The worker tier holds each worker's own info lines, one shard and no replica. The storage tier holds everything else, with a copy on each of its three machines.

We split by severity, not by source. Info lines are both the bulk and the lines least likely to matter, so they stay on the worker that wrote them and are disposable. Under this rule 96.94~\% of the \textit{O2} process-tree family stays local. Warnings, errors and every \textit{InfoLogger} record are rare and are the lines people look for, so they cross the wire once and are copied three times. The journal follows the same idea through its own field. Each journal entry carries a priority from 0, an emergency, to 7, a debug message. Priorities 0 to 4, warnings and worse, go to the storage tier. Priorities 5 to 7, notices, information and debug messages, stay on the worker. The 2025 reference design split by source: one program's logs local, another's central~\cite{ref:papadopoulos2025}. That rule ships the whole info bulk of a chatty program across the network and keeps the errors of a quiet one on a single disk. It also needs four edits in step for every new log source.

\subsection{Native system services on staging, containers on the farm storage machine}\label{sec:why-systemd}

On staging every component runs as a system service. It is installed from the vendor's RPM package, and \textit{systemd}, the Linux service manager, starts it, restarts it and sends its output to the journal. A person operates it with the same commands as any other service on a CERN machine. The alternative was a container runtime on top of the \textit{OpenStack} virtual machines, as in the local development stack. That is a second runtime to install, patch and debug. \textit{Kubernetes} was planned in detail and dropped, because the EPN farm has no \textit{Kubernetes}.

The farm gives the storage tier one shared infra machine, not three. The supervisor decided to keep the three-node tier as three \textit{Podman} containers on that machine, rather than collapse it to one native node. A container is a program run with its own file system and network ports, isolated from the rest of the machine. Cloning the tested three-node tier is cheaper than collapsing it and undoing that later. The same deployment code installs the RPM when a machine carries one node, and containers when it carries several. Tier settings, replica counts, templates and monitors do not change. Three replicas on one disk rehearse no fault tolerance. If that machine dies, the storage tier dies with it.

\subsection{The surfaces: \textit{OpenSearch Dashboards} and a standalone shifter view}\label{sec:why-surfaces}

\textit{OpenSearch Dashboards} is the web interface of \textit{OpenSearch}, built by the same project and released with it. It holds two of the four surfaces behind the one web address.

The maintainer cockpit is a dashboard in \textit{OpenSearch Dashboards} for the people who maintain the platform. It answers one question: is the pipeline healthy? It shows which collectors are healthy, degraded or down, how many records each has shipped and lost, the cluster status, heap use and index sizes, and the open episodes and active alerts. A shifter never needs it.

Discover is the free-form search page of \textit{OpenSearch Dashboards}~\cite{ref:osddiscover}. A person picks a time range, types a query in the search bar and adds filters on fields, for example host or run number. Discover then lists the matching records and draws their count over time. One search box covers every log family at once. It serves a physicist with a real question about the archive.

We chose \textit{OpenSearch Dashboards} because it ships the screens for anomaly detection, alerting and notifications in the same package as the store. There is no second product to install, and a person signs in once. The 2025 reference design used \textit{Grafana} for display and alerting~\cite{ref:papadopoulos2025}. \textit{Grafana} can read \textit{OpenSearch} as a data source, but the detectors and monitors would still be configured through \textit{OpenSearch}, so a maintainer would work in two interfaces. We did not compare \textit{OpenSearch Dashboards} and \textit{Grafana} on numbers.

The shifter view is the page the person on shift watches. It holds the live page, which shows what arrives now, and the Templates page, which shows the template catalogue, its counts and the open episodes. It is a standalone web page behind the same address, not an \textit{OpenSearch Dashboards} plugin. A plugin must match the major, minor and patch release of \textit{OpenSearch Dashboards} exactly~\cite{ref:osdplugins}. Every security patch would force a rebuild of the plugin, and a failed rebuild would take the shifter's page down. The live page reads only the live-lane topic and never queries the cluster, so it keeps working when the cluster is down. A general query tool belongs in \textit{OpenSearch Dashboards}, and Discover is that tool. The operator view close to \textit{InfoLogger} is not built.

\subsection{The stamper in band}\label{sec:why-stamper}

A template is the skeleton of a log line, with every variable token replaced by a wildcard. The stamper is a small \textit{Python} service beside the collector on every worker. It names the template of every record in band: on the record's path, before the record is indexed. It uses \textit{drain3}~\cite{ref:drain3}, the same template miner that mined the archive.

We placed it on the worker so that no raw line leaves its machine to be named, and so that both tiers receive the template field once. The collector hands each chunk to the stamper over a local socket with \textit{Fluent Bit}'s own forward protocol, and gets it back stamped. An HTTP hop was rejected because it replaces the record's own time with its arrival time.

We did not port the miner into the collector. \textit{Fluent Bit} filters are written in C, \textit{Lua} or \textit{WebAssembly}, and none can host \textit{drain3}, which is \textit{Python}. A port would be a second implementation of the masker, the step that replaces variable tokens, and its exact output is the template's identity. Section~\ref{sec:logtext-miner} gives the reason every other template miner lost, and describes the masker rewrite. What the stamper costs beside a running collector is not measured.

\subsection{Detection on numbers, inside the cluster}\label{sec:why-detection}

The platform must catch three kinds of trouble: known cliffs, unfamiliar shapes and slow drift. Threshold monitors, Random Cut Forest detectors~\cite{ref:rcf} and trend rules each catch one kind (Section~\ref{sec:design-watch}). A Random Cut Forest learns the usual shape of a number from the stream itself, so it needs no labelled faults. ALICE has none. All three lanes run inside \textit{OpenSearch}, as the detection and alerting plugins that ship with it, so they add no service to keep alive. No learned model reads the log text in the detection path. Section~\ref{sec:logtext} gives the reasons, and Section~\ref{sec:metrics} gives the detectors and rules.

\subsection{Episodes, and \textit{Alertmanager} as messenger}\label{sec:why-episodes}

A firing monitor writes a new alert row every time it runs. A dead collector therefore produces thirty rows in thirty minutes, from several monitors at once. The projector reads all of those rows and groups the ones that describe the same trouble on the same thing into one episode, with a start and an end. Without it, a person would see the same alert every minute.

\textit{Alertmanager}~\cite{ref:alertmanager}, from the \textit{Prometheus} project, decides when a person is told and how often. It groups alerts into one message, holds a timer before it sends, lets a person silence a rule for a time, and routes each alert to a receiver. It stayed from the 2025 reference design. It keeps alerts in memory only. Its clients are expected to re-send every firing alert at regular intervals~\cite{ref:amapi}, and it forgets an alert five minutes after the last post. So the projector re-posts every open episode every 30~seconds.

Inhibition is an \textit{Alertmanager} rule where one firing alert silences another that it causes, for example a dead cluster silencing every monitor that reads from it. It is built and ships switched off. All 22 cause-and-effect links between alerts are unproven, because no fault injection has shown that the cause always comes first.

\subsection{Kafka between the collector and the store}\label{sec:why-kafka-store}

\textit{Kafka}~\cite{ref:kafka} is a message bus: a set of brokers that store records in order and let many readers consume them at their own pace. The 2025 reference design put \textit{Kafka} between every collector and the store~\cite{ref:papadopoulos2025}. A bus buys two things. Decoupling means a burst from the writers does not reach the store at once. Durability means records survive while the store is down.

The soak rejected it on both counts. For decoupling, one worker's stack sustains about 42,000 records a second. The busiest second any worker had in six months was 78, so the margin is 538 times. For durability, only \textit{InfoLogger} records are lost in a storage outage, and the collector's 256~MB disk buffer holds 17.4~hours of them at a median worker's rate. The cost is real: three brokers on memory the staging machines do not have, and the tier rule would then live in two places. Section~\ref{sec:eval-kafka} gives the four conditions that reopen the decision.

\subsection{Kafka for the live lane}\label{sec:why-kafka-live}

The live lane is the second copy of every record that leaves a worker. Each collector writes it to one \textit{Kafka} topic, and the shifter view consumes it. The bus carries the live lane only, and it exists to decouple the collectors from the shifter view. The collectors' disk buffers already survive a restart, so durability alone would not justify it. Because the shifter view is the topic's one consumer, moving it to another machine changes one place instead of the configuration of more than 200 collectors.

It must be Apache \textit{Kafka}, because CERN requires fully open-source software. \textit{Redpanda}, the usual alternative, is under the Business Source License, which is source-available and not open source~\cite{ref:redpanda}. The bus is the collector's primary live-lane output. It cannot be a fallback, because the collector held at release 4.0.1 has no route for a failed output.

\subsection{Deployment: Ansible}\label{sec:why-deploy}

The agent decided it. An agent is a program the deployment tool installs and leaves running on every machine. \textit{Ansible}~\cite{ref:ansible} has none. It connects over SSH when a person starts a run, pushes the configuration and leaves. CERN hosts take no long-running agent from this project, so nothing new runs on them. The same tool also creates the virtual machines. Table~\ref{tab:deploy} lists the candidates.

\textit{Puppet} with \textit{Foreman} is the CERN standard, and ALICE build machines already run it. It repairs drift by itself on a timer. Each machine needs a \textit{Puppet} agent and a certificate signed by the \textit{Puppet} server~\cite{ref:puppetcsr}. That is likely right for the farm. It is wrong for five machines that one person deploys by hand. \textit{Salt} fans out fastest, but only at farm scale. \textit{Chef} needs a second language. Both put an agent on every node. \textit{Terraform} builds machines well, and its vendor states that it is not a configuration management tool~\cite{ref:terraform}. We would need a second tool to configure the machines. We did not consider shell scripts, because a script does not check the state a machine is left in.

Three design rules followed. Placement is data: one inventory file says where each service runs, and moving a service to another machine changed no code. Every step converges: a failed run is simply run again, and monitors and detectors are created by name, never twice. Twelve checks fail the deploy rather than report success.

\subsection{Cockpit metrics beside \textit{Telegraf} and Mimir}\label{sec:why-metrics}

The cockpit needs numbers about the log pipeline itself: is each collector alive, how far behind is it, how full is the cluster. The poller is a small service on the control host that samples the cluster every 30~seconds. Each collector pushes its own health sample, so nothing reaches into a worker to ask. The roster is the list of collectors that must run, and the poller marks any rostered collector that falls silent. A dead collector sends nothing, so only the roster lets the platform notice it.

CERN already runs \textit{Telegraf} and \textit{Mimir} for machine metrics. \textit{Mimir}, from \textit{Grafana} Labs, stores \textit{Prometheus} metrics for the long term. Our cluster and node samples duplicate part of that estate. The roster and the absence logic have no equivalent there, so they stay. Whether the existing estate takes over the overlapping samples is open.

\subsection{Shared code as one package}\label{sec:why-package}

About 31,000 lines of \textit{Python} run the services. The code that more than one service uses lives in one versioned \textit{Python} package that every service installs, and no service keeps its own copy of a shared module. A file is in the package when more than one service uses it, another module imports it, it needs third-party libraries, or it needs tests. We rejected a port of the services into \textit{OpenSearch} plugins, because a plugin must match the exact \textit{OpenSearch} release and needs a \textit{Java} toolchain. Appendix~\ref{app:upstream} lists the existing deployment roles we weighed and did not use.
