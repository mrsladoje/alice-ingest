\section{The design}\label{sec:design}

\loggy{} is one \textit{OpenSearch} cluster, split into two tiers by severity.

\subsection{One \textit{OpenSearch} cluster, two tiers}\label{sec:design-tiers}

The worker tier runs on every EPN in the target design. The collector reads the five collected sources of Table~\ref{tab:sources}. The stamper beside it names every line's template, the skeleton of the line with every variable token a wildcard, before indexing. The health sample pushes the collector's heartbeat up. The local \textit{OpenSearch} data node holds one index per worker. The four share the worker's four-core budget of Section~\ref{sec:problem-constraints}. Memory is a 384~MB cap on the collector and a 1~GB heap on the local node.

\begin{figure}[htbp]\centering\includegraphics[width=0.92\textwidth]{fig02-architecture.pdf}\caption{The bulk stays on the worker tier, \textit{InfoLogger} and every line above info cross once to the storage tier, and every watcher pushes its numbers up.}\label{fig:arch}\end{figure}

The storage tier is three replicated nodes, each a cluster manager and a data node. An index is split into shards, and a replica is a copy of a shard on another node. Two of the three nodes must agree, so the tier survives the loss of one.

The three storage nodes are also the control host, the background host and the shifter host. The control host holds the one web door every person opens. Behind it sit \textit{Dashboards}, the maintainer's screen, and \textit{Alertmanager}, which decides when a person is told. The control host also runs the poller, the roster of collectors that must run, the catalogue maintenance and the receiver. The background host runs the projector, which turns alerts into episodes, and the trend rollup. The shifter host serves the shifter view, the page the person on shift watches.

Staging is five machines: two workers and three storage nodes. The farm pilot is three workers and three containers on one infra machine.

A \textit{Kafka} bus carries the live lane only (Figure~\ref{fig:arch}). The live lane is the second copy of every record that leaves the worker. That is every \textit{InfoLogger} record at any severity, the daemon log and every line above info severity. Every collector writes it to one topic, and the shifter view is the one consumer. Moving the shifter view to another machine changes that one consumer and no collector configuration.

Table~\ref{tab:indices} lists the index families. The farm sets three primaries, one per storage node, because one primary funnels all \textit{InfoLogger} through one machine. No farm run has carried real volume.

\subsection{Walkthrough: one error line, from an EPN to a screen}\label{sec:design-walk-error}

An error line crosses the wire twice (Figure~\ref{fig:errorline}).

\begin{figure}[htbp]\centering\includegraphics[width=0.9\textwidth]{fig03-error-line.pdf}\caption{An error line is stamped on the worker, crosses the wire to the storage primary and two replicas, and again to the live lane.}\label{fig:errorline}\end{figure}

\begin{enumerate}[itemsep=3pt]
\item \emph{The line appears in a file.} An \textit{O2} process writes an error line to its own log file, and the collector tails that file. The path gives the machine and the program, and the line gives the event time. The collector adds its own accept time and a document identifier unique to the record.
\item \emph{The raw severity decides the route.} A routing rule reads the severity as the line wrote it. Info, debug and trace take the local route, and this error takes the central one. A line the collector cannot parse also goes central, because a lost error costs more than an extra stored line.
\item \emph{The stamper names the template.} The collector moves records in chunks. Each chunk crosses a local socket to the stamper, which masks the variable tokens and matches the line against its template tree. The chunk comes back with a template version and a status on every record. Only returned chunks can reach the store, so no record is indexed unstamped.
\item \emph{Processed on the worker, stored on the storage tier.} The collector writes only to the store node on its own worker. There the ingest pipeline, a set of processors run on every document before storage, adds the ingest time and two lags. The first lag is the line's age when the collector read it, the second its trip into the store. The pipeline also maps every source's severity spelling to one vocabulary. The finished document then crosses the wire once, to the storage node holding the primary shard of \code{application-logs-central}. That node copies it to two replicas on the other storage nodes.
\item \emph{A second copy goes to the live lane.} The collector also writes the record to the live-lane topic on the \textit{Kafka} bus of Section~\ref{sec:design-tiers}. The shifter view consumes that topic, keeps the last 500 records in memory and streams them to every open browser. It never queries the cluster, so it keeps working when the cluster is down.
\item \emph{Two screens can find it.} Discover, the search screen of \textit{Dashboards}, finds the line in the central index. The shifter view's query lane searches the same index, capped at 20,000 rows. Both reads go to the storage tier and leave the worker alone.
\end{enumerate}

\subsection{Walkthrough: an info line stays on its worker}\label{sec:design-walk-info}

Most of what the farm writes is info level. This is the cheap path, and the storage tier never sees it.

\begin{enumerate}[itemsep=3pt]
\item \emph{A \textit{DDS} info line takes the local route.} \textit{DDS} writes info lines by the thousand. The collector joins an event that spans several lines, such as a banner, into one record. The routing rule sends it to the local route.
\item \emph{It is still stamped and processed.} Every family passes the stamper and the ingest pipeline on the worker, so the template counts cover the bulk too.
\item \emph{It lands in a shard on the same machine.} Each worker has one index of its own, with one shard and no replica (Table~\ref{tab:indices}). A placement setting pins that shard to the worker's own node, so the line never crosses the wire. That keeps the network free for reconstruction data. Under severity routing 96.94~\% of the \textit{O2} process-tree family stays local.
\item \emph{Three readers use it.} The trend rollup reads the index every ten minutes. Three detectors read it every minute, and their three slow twins every 30 minutes. The shifter view fetches a few real lines from it when a person inspects a template. If the worker dies, its raw lines die with it. The rollup rows, template counts and detector results survive, and the rules run on those.
\item \emph{The live lane never sees it.} Across more than 200 workers the info bulk would saturate the wire and flood the live view. Only a search over the worker indices finds an info line, and that search is as slow as the slowest worker. Section~\ref{sec:why-cluster} explains why we accept that cost.
\end{enumerate}

\subsection{Inside the collector}\label{sec:design-collector}

The collector stores nothing (Figure~\ref{fig:collector}).

\begin{figure}[htbp]\centering\includegraphics[width=0.9\textwidth]{fig04-collector.pdf}\caption{A line takes five steps inside the collector. The 64 chunks it holds in memory are about 128~MB of the 133 to 228~MB it uses under load.}\label{fig:collector}\end{figure}

Flushing every second instead of every 5~seconds cut the collector's processor cost by 24.5~\% and its peak memory by 28.0~\% (Section~\ref{sec:eval-collector}).

At most 64 chunks sit in memory, about 128~MB. The documented worst case is twice that with a 20~\% margin, roughly 307~MB.

An output is the collector's connection to one destination. Each output has a 256~MB disk buffer: when the store does not answer, chunks spill to disk. At a real worker's rate it holds hours, but it is not durability: a lost machine loses its records.

A resend cannot duplicate. The document identifier, node id plus boot id plus a counter, is the record's id in the store. The output writes with create, which the store refuses when that id already exists.

\subsection{Templates in band}\label{sec:design-templates}

Every record carries its template version before it is indexed (Figure~\ref{fig:templates}). A template widens as the stamper sees more lines, and each state is one version.

\begin{figure}[htbp]\centering\includegraphics[width=0.86\textwidth]{fig05-templates.pdf}\caption{The stamper names each line on the worker, publishes counts every five minutes, and two hourly audits prove the counts add up.}\label{fig:templates}\end{figure}

The stamper runs \textit{drain3}, a template miner \cite{ref:drain3}. A masker replaces varying tokens with placeholders, then one tree per family turns a literal that varies between lines into a wildcard. Every record leaves with a status: matched, new or no template. An empty message, or one over 4,096 characters, is indexed in full with no template.

The stamper holds at most 20,000 templates per worker, 4.7 times the 4,221 templates one tree mined from 55,963,050 archive lines (Section~\ref{sec:eval-templating}). The shipped service evicts the least recently used template at that ceiling. The soak showed that an evicted template rebuilt later resets its published count to one. The recommended change, to stop learning and keep counting, is open.

The catalogue is one index with one document per template version the farm has seen, plus the results of the checks below. Every 300~seconds the stamper publishes one bucket document per family and window: a total and a count per version.

Two audits run hourly. The stamper recounts the previous hour locally. The first check proves that no count is lost: up to 5,000 hourly buckets sum to their family totals. The second proves that no record is counted twice. Neither the central nor the \textit{InfoLogger} index holds more records of a template version than the workers stamped.

Two hourly rules read the catalogue. One fires on a template catalogued in the last hour. The other fires on any failed check in the last two hours.

A search for a template must also find its older, narrower versions. Within one family and token count, a wider version covers a narrower one when, at every position, it holds a wildcard or the narrower's token. That relation groups the versions, so no separate identifier is stored. Templating is built for search and the catalogue. Two choices are open: catalogue maintenance as store policies plus monitors, and the bucket indices as a rollover alias.
