Why it
must change

The design fits the farm it was written for. Run 4 is not that farm, and the machine is only off once.

LHC switched off 29 June 2026
Run 4 first beam June 2030

  • Not scalable One server and one SQL table for the whole farm. You can add nodes; there is nothing to add at the other end.
  • Not durable Past 500 messages a second a process writes to a file in /tmp, then drops. It recovers only below 10 a minute, so the record thins exactly during an incident.
  • Not searchable Message bodies sit in an unindexed text column, and archiving renames the table. Free-text search is a scan, across tables chosen by hand.
  • Not complete Only what is injected through the API arrives. DDS task logs and process stdout stay on node disks.
  • Not extensible One script bridging to a syslog socket is the way out. No bus, and nowhere to attach detection or alerting.

Why this
design

The five machines are only the shape of it. These are the decisions underneath, and the cost we accepted for each one.

  • The bulk never travels Application logs at info severity are most of the volume and the least of the value. They are written to the node that made them and go no further. That the bulk tier never crosses the wire was a requirement, not an optimisation.
  • Split by severity The obvious cut is by source — DDS here, stdout there. That ships the whole stdout bulk across the farm and discards DDS errors along with it. Severity cuts the same stream where it matters: volume on one side, value on the other.
  • Workers stay cheap A worker is a data node and nothing else — never cluster manager, no replicas, no dashboards. Thread pools are capped explicitly, or OpenSearch would size itself to all 128 cores of an EPN.
  • Storage takes the weight Only we run these three, so they carry the cluster manager, every replica, the dashboards and the analytics. They run no collector and no producer, and nothing on them competes with reconstruction.
  • One machine may die Three storage nodes give a quorum of two and two replicas of everything valuable, so losing one costs nothing. Losing a worker costs that worker's info logs. That is the trade.

What is
not built

Five things are missing, and none of them is a surprise. Each has a written reason for waiting and a cost we already know.

Trigger for the queue: a third consumer
Security plugin off, firewalld is the boundary
Detector timings are design values, not measured

  • The queue is not built Fluent Bit discards its oldest chunk when the disk queue fills; it does not push back on the input. An Apache Kafka commit log would survive a collector restart and a storage outage. It costs three brokers and a second system to run.
  • The names are ahead of the code This deck uses application-logs-local and application-logs-other. The code still ships generic-log-*, in 35 files that are not READMEs: templates, retention, detectors, monitors and the cockpit.
  • No alert reaches a person Alertmanager routes today, but its only receiver is a webhook back into the cluster. An external channel is a config change. Grouping is the real work: one fleet-wide breach emits about 215 alerts.
  • The model budget is unproven Three days of the archive hold 211, 214 and 215 distinct hostnames, not the 31 assumed. Ten per-host detectors at that count is about 2,100 models, against a budget estimated at 256 for this heap.
  • The shifter's view is missing The Operator Cockpit is not built, and it cannot be finished without EPN access. It has to copy the interface shifters already use, because a tool that needs training does not get used.
